# Postman collection

**English** | [简体中文](README.zh-CN.md)

This folder contains 29 requests for the **Camunda 8.9 Orchestration Cluster REST API**, matching this repository's `1-17.bpmn`. The Java application is a job worker, not a patient CRUD HTTP server. Requests go directly to Camunda at `http://localhost:8080` by default.

## Import and prerequisites

1. Import `Hospital_Patient_Pathway.postman_collection.json` and `Local_Camunda.postman_environment.json` into Postman.
2. Select **Hospital Pathway - Local Camunda 8.9**. Set `baseUrl` without a trailing slash or `/v2`.
3. Start Camunda 8.9. The collection defaults to **No Auth**. For an authenticated cluster, configure its required authentication on the collection; all requests inherit it. Keep credentials local.
4. Set Postman's file working directory to `HospitalPatientPathway`. In the deployment request, check **Body → form-data → resources**. If the imported file references are unresolved, reselect `1-17.bpmn` and all **16 root `.form` files** together. Upload them in one request because forms use deployment binding. Let Postman generate the multipart Content-Type and boundary.
5. Start the worker from `HospitalPatientPathway/java` (PowerShell):

   ```powershell
   .\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=--hospital.simulation.scenario=none --hospital.simulation.auto-responder-enabled=false"
   ```

Use Postman Desktop or a local agent that can access the cluster and deployment files. A cloud runner's localhost does not refer to your computer.

## Run an example

1. Send the topology, deployment and definition search requests in **01 - Setup**, individually.
2. Send **04 - Create hospital instance**. Empty environment values for `referralId` and `patientId` are populated with unique identifiers. A successful response saves `processInstanceKey` for subsequent searches.
3. In [Tasklist](http://localhost:8080/tasklist), complete **Register referral in PAS and check documents** (`R1_RegisterCheck`) for that instance. The creation request supplies fictional sample data. Keep the worker running: form completion invokes the validation listener.
4. Once the instance reaches `Gateway_ExternalTriggerRouter`, select **ONE** request from **02 - Entry events**. Choose **P01 - Incoming referral** for the referral path or **P15 - Monitoring request** for the reporting path.
5. Continue human tasks in Tasklist. Send relevant requests from **03 - Patient and laboratory responses** when the process waits for them. Acceptance/alternative date/decline and consent/refusal are alternative branches.
6. Inspect instance status, user tasks, variables and incidents with **04 - Observe current instance**, or open [Operate](http://localhost:8080/operate).

**Do not run the entire collection sequentially.** This is an interactive toolkit with mutually exclusive branches, not an automated end-to-end test suite. To test another entry route, create a separate instance and complete its referral form first.

## Variables and behavior

| Variable | Purpose |
| --- | --- |
| `baseUrl` | Camunda server; defaults to `http://localhost:8080` |
| `processDefinitionId` | `Process_Hospital_Integrated`; creation uses the latest active version |
| `referralId` | Correlation key for entry events and most responses |
| `patientId` | Correlation key for laboratory results |
| `patientName` | Fictional name used when creating the instance |
| `incidentReference` | Same business identifier for interruption and restoration; use a unique value for each new interruption |
| `processInstanceKey` | Saved on successful creation, or manually set for an existing instance |
| `today` / `preferredDate` | Request-local UTC dates generated by the collection script: today and 14 days later |

Before a new run, clear `referralId` and `patientId`, or supply new unique values. Keep them stable during that run. If you change the referral ID in Tasklist, update the environment before publishing messages. For existing instances, supply their actual identifiers.

The current model has only the plain start event `Start_Tasklist`. Publishing an entry message alone **does not create an instance**. Create it, complete the form, then choose an entry message. Message names include the required `Hospital pathway: ` prefix.

Messages use a **900000-millisecond (15-minute)** TTL. Each Send generates a new `messageId`; resending therefore publishes a new message. To test deduplication, replace that dynamic value with a fixed ID. HTTP 200 confirms publication, not correlation or business completion. Inspect the instance and its current element to confirm progress.

Disable the scheduled automatic responder for manual testing. Workers still simulate replies from scheduling, funding, payment and other requested services. Before testing appointment acceptance/alternative date/decline, check `hospital.simulation.patient-decision`: the worker's simulated reply may arrive first. Direct Postman requests also bypass the incoming-event audit recording in `ExternalEventService`.

Search results are eventually consistent; resend if a recent change has not appeared. Searches return up to 100 records per page (20 for definition search); use the returned pagination cursors for more results.

## Validation and references

Requests include status assertions, instance/message response checks and search-result checks. JSON, Postman Collection v2.1 schema, deployment file references, and message names/correlation keys were checked against the BPMN and Java catalogue. End-to-end validation against a running cluster has not been performed.
